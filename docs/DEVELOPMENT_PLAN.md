# 開発計画：5分戦記 / 5 MINUTE ORDERS

作成日: 2026-09-09

状態: 提案。既存の採用要件を前提とする進め方の案であり、未決定ルールの採用や実装完了を意味しない。
現状はM0の開発基盤（起動シーン・ターンフェーズ契約）。ゲームルール、AI、保存は未実装。
要件は[SPEC 001](specs/001-prototype.md)、節目は[ロードマップ](ROADMAP.md)を参照する。

## 1. 基本方針

「仕様固め・クリエイティブ・マニュアル・実装・テストプレイ」の5区分で作業を管理する。
ただし、各区分を一度ずつ完了する進行にはしない。次の順序で小さく反復する。

**最小ルールと説明書 → 紙上検証 → 仮素材の実装 → 試遊 → 仕様修正 → 本素材・説明の仕上げ → 実機試遊・調整**

最初の目標は「外部サーバーなしで、2国家のAI戦を開始から勝敗まで遊び、保存・再開できる検証版」。
ストア公開版の完成とは分ける。まず、敵の意図を予想して攻撃・防衛を決める体験が成立するか確かめる。
5分は1ターンの命令を短時間に収める設計制約であり、1試合の長さや強制カウントダウンではない。

## 2. 5つの作業区分

| 区分 | 主な作業と成果物 | 次へ進める目安 |
| --- | --- | --- |
| 仕様固め | 最小ルール、具体的な解決例、画面の流れ、検証したい仮説をSPEC化 | 同じ盤面・命令について解決結果を一意に説明できる |
| クリエイティブ | 地図・文字・色・アイコンの見本、必要素材一覧、指揮官・紋章・戦記の表現 | スマホで状態と操作を見分けられ、少量の素材で方向性を確認できる |
| マニュアル | 初期の1枚ルール、クイックスタート、ゲーム内ヘルプ、用語集 | 初見の人が説明を読み、自分で命令を確定して結果を理解できる |
| 実装 | 決定的なルール解決、情報制限、UI、AI、ローカルDB保存・再開 | 2国家で1試合が完了し、対象端末でオフライン再開できる |
| テストプレイ＆バランス調整 | プレイ記録、操作時間、読み合い・停滞の評価、修正と再検証 | 主要な不具合を解消し、選択の理由と結果が理解され、再プレイにつながる |

### 仕様固め：実装する部分から決める

原案全体を完成仕様にする必要はない。まず次を決め、正常例と境界例をSPECに併記する。

- 勝利・敗北・引き分け条件、同時首都陥落、試合が終わらない場合の扱い。
- 初期配置、領地の隣接関係、軍団と指揮官の関係、開始時1人から検証範囲の1〜3人を扱う方法。
- 命令の種類、未入力時の動作、変更できる時点、確定前の不正命令の拒否。
- すれ違い、同じ領地への同時侵攻、味方の合流、移動先が空いた場合の占領。
- 戦闘の勝敗・損害・防衛の効果、同値、退却先がない場合、指揮官敗北。
- 見える領地・軍勢、過去の情報の扱い、結果ログで公開できる内容。
- 経済・補給・補充を最初の検証に含めるか。省く場合も、軍勢が減るだけで停滞しないか確認する。

6〜9領地、1指揮官1命令、未入力は防衛などは現SPECの仮案。採用時に状態を明記する。
初期試合の目標ターン数・所要時間は仮説として置き、試遊結果を受けて調整する。
国家差、特殊能力、加入イベントは基本の読み合いを確認した後のM4で判断する。

### クリエイティブ：方向性を早く、本制作は遊びの確認後に

最初に作るのは、地図・命令入力・ターン結果の画面ラフと、小さなスタイル見本。
文字サイズ、余白、国家色、味方／敵／未観測の表示、命令アイコンを先に揃える。
日本語フォントと識別しやすい記号は、仮素材の段階から必要。色だけに情報を依存させない。

素材制作の優先順位案:

1. 必須: 読める日本語、地図の状態表示、選択・移動・防衛・確定の表示、結果ログ。
2. 体験の仕上げ: 2国家の紋章、検証用指揮官の肖像、短い戦闘・戦記文、必要な効果音。
3. 検証後: 多数の肖像、イベント挿絵、装飾、タイトル画像、販促素材。

最初は肖像1点・紋章2点など少量で画風と縮小時の見やすさを確認し、必要量を決める。
素材一覧には用途、サイズ、状態（仮／本番）、出典・ライセンスを記録する。
実際に追加した素材の権利情報は `game/assets/README.md` に残す。
本制作は画面構造が安定してから進める。外部試遊前には説明に使う画像を実装画面に揃える。

### マニュアル：仕様を確かめる道具として先に書く

実装前に「何を目指し、何が見え、どう命令し、何が起こるか」を1枚にする。
説明できないルールや例外があれば、仕様に戻して整理する。
開発者向けの厳密なSPECと、プレイヤー向けの遊び方は分ける。

- 早期: 1枚ルールと、攻撃・防衛・すれ違いなどの具体例。
- プレイ版: 初回の命令確定までを案内するクイックスタートと、結果の読み方。
- 試遊前: 実画面を使う操作説明、用語集、よくある疑問、保存・再開の説明。
- 公開準備: 検証済み機能に一致する最終版をアプリ内に同梱し、オフラインで読めるようにする。

ルール変更時はSPEC・コード・テスト・関連する説明を同じ変更で同期する。
長い説明が必要になったときは、説明の追加だけでなく操作やルールの簡略化も検討する。

### 実装：小さな完成単位で積む

| 順序 | 実装単位 | 確認すること |
| --- | --- | --- |
| 1 | マップ・国家・指揮官・軍団・命令・勝敗 | 状態と命令の不正を拒否できる |
| 2 | 移動・衝突・戦闘・退却・占領の同時解決 | 固定スナップショットから解決し、入力順に結果が依存しない |
| 3 | プレイヤー別Observationと結果 | UI・AI・ログへ秘密情報を渡さない |
| 4 | 仮素材UI、命令確認、結果、最小AI | 戦況確認→命令→確定→結果→次ターン→勝敗が通る |
| 5 | 選定済みローカルDBによる保存・再開 | バージョン付きデータを原子的に保存し、中断後に整合した状態へ戻る |
| 6 | 本素材、ヘルプ、実機での操作改善 | 読みやすさ、タップ、セーフエリア、中断・復帰を確認できる |

UI→application→domainの依存を維持する。DBはinfrastructureで扱う。
AIはプレイヤーと同じ情報制約で動き、まず合法な命令を出すところから始める。
その後、攻撃・防衛の方針に傾向を持たせ、読める手がかりと単調さの両方を検証する。
オンライン、通知、課金、アカウント、外部DBは初期版に含めない。

DB方式の検証は序盤に行う。対象OSの書き出し、同梱、通信なしの読み書き、
トランザクション・中断復帰、ライセンスを確認してADRと依存台帳に選定結果を残す。
採用候補の調査時には、その時点の公式情報を確認する。本計画では製品を決定しない。
最初の1OSで実機ループを早く確立し、両OS対応を掲げる前に双方を検証する。

### テストプレイ＆バランス調整：最終工程に閉じ込めない

序盤は少数の盤面を紙上で解決し、仮素材のプレイ版ができたら毎回遊ぶ。
自動テストは正しさ、試遊は理解・操作・面白さを確かめる役割に分ける。

| 観点 | 記録すること | 改善の方向 |
| --- | --- | --- |
| 読み合い | 敵の予想、根拠、選んだ命令、結果、次の手 | 手がかり不足、常に同じ正解、AIの単調さを切り分ける |
| 5分の制約 | 戦況確認・思考・入力それぞれの時間、迷った画面 | 操作を短くし、考える時間を残す。総時間も確認する |
| 勝敗・停滞 | 国家・初期配置・先行有利、試合ターン数、守り続ける展開 | 地形、勝利条件、戦力配分、防衛の効果を見直す |
| 劣勢の選択 | 劣勢になった時点と、残っていた有効な作戦 | 必ず逆転させず、読みが当たれば挽回できる選択を確かめる |
| 理解・継続 | 説明で詰まった箇所、結果の理解、再プレイ希望と実施 | UI・説明・ルールのどこに原因があるか確認する |

初回は3〜5人程度、その後5〜10人程度の試遊を提案する。募集・連絡は別途実施判断する。
少人数の勝率だけでバランスを確定しない。盤面・国家を入れ替えた比較と行動理由を併用する。
記録にはビルド、ルール版、seed、初期配置、命令、変更点を含め、手元で再現できるようにする。
収集は手元の記録と任意フィードバックから始め、ゲームのネット接続を必要としない。
1回の調整では仮説を絞り、変更前後を比較する。面白さに問題がある場合は仕様へ戻る。

## 3. 節目と進行判定

| 節目 | 成果物 | 完了条件 |
| --- | --- | --- |
| M1-A 最小ルール合意 | SPEC更新、1枚ルール、紙上の解決例 | 衝突・退却・勝敗・公開情報の主要な未決定事項を解消 |
| M1-B ルール検証 | domain実装、行動テスト、DB・実機方式の検証記録 | 同時解決・決定性・情報制限を検証し、保存実装前にDB方式を選定 |
| M2-A 仮素材のプレイ版 | 小マップ、命令UI、結果、AI | 最初から最後まで1試合遊べ、読み合いの記録を取れる |
| M2-B 保存できる検証版 | ローカルDB、保存・再開、暫定ヘルプ | 通信なしでプレイ・再起動・再開し、中断保存でも壊れたターンを露出しない |
| M3 実機試遊版 | 必要な本素材、実画面の説明、試遊記録 | 日本語・タップ・安全領域・復帰・命令時間を対象実機で確認 |
| M4 拡張判断 | 学びと次版の範囲 | 継続・基本ルールの修正・国家差や能力の小規模追加を判断 |

3指揮官の実ゲーム検証に加え、7指揮官の操作モックで終盤の操作量を確認する。
これは初期ゲームの指揮官上限を拡張する決定ではない。
M3後は、機能追加前に重大不具合と理解・操作の問題を解消する。
ストア公開は配布対象、最低OS、署名、権利表記、掲載内容を別途確定してから判断する。
オンライン化はM4以降の独立した判断であり、検証版完成の条件にしない。

## 4. 最初に進める作業

1. 「何を予想して、どんな選択が変われば面白いか」を、具体的な盤面3例で書く。
2. 勝利条件、戦闘・退却、同時移動、観測情報を候補と具体例で比較し、最小ルールを決める。
3. 1枚ルールと、地図→命令確認→結果の画面ラフを作り、紙上で数ターン回す。
4. 初回実機のOS・端末を決め、書き出しとローカルDBの小さな技術検証を行う。
5. SPECに決定内容を反映してM1の実装を始め、最短でM2-Aへつなげる。

担当の目安は、プロダクト所有者が面白さ・世界観・仕様案の採用を判断し、実機で試遊すること。
Codexは仕様候補・具体例・素材案・実装・テスト・記録整理を支援する。
作業は「成果物・完了条件・依存先」が分かる小単位にし、毎回遊べる状態へ近づける。

稼働時間と対象端末が未確定のため、発売日・週数はまだ約束しない。
最初の仕様検討と技術検証の実績をもとに、M2-Aまでの工数を見積もり直す。
定期的な振り返りでは「今遊べること・分かったこと・最大の問題・次の検証」を更新する。
販促は[既存の方針](MARKETING.md)に沿って制作物を再利用し、試遊可能になるまでは検証中と明記する。

## 5. 変更時の品質確認

- GDScript: `make format` → `make check`。ルール変更には行動・失敗・決定性・情報アクセスの該当テストを追加。
- UI・素材: レンダリングと実操作を確認。スマホで日本語・縮小・タップ・セーフエリアを確認。
- 保存: オフラインの新規開始・保存・終了・再開・保存途中の中断を確認。
- 文書: SPEC・マニュアル・ロードマップ間の整合性と `git diff --check` を確認。
- 未検証の端末・書き出し・CIを成功扱いにせず、各節目に残る制約を記録する。
