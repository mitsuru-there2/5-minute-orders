## 1. M1で確かめる体験

限られた情報から敵の進路を予想し、攻撃・防衛・迂回の選択を変える価値があるかを確かめる。
次の3点を検証仮説とする。成立を確認した事実ではない。

- 敵の進路を読んで待ち構えると、無計画に進軍するよりよい結果になる。
- 正面で不利でも、敵が動いた隙に別経路を通る選択が残る。
- 敵の位置・規模には判断の手がかりがあり、命令そのものは分からない。

M1ではルールの一意性・決定性・情報制限とCLI操作を検証する。
面白さの確定、スマホの操作時間、完成AIの強さはM1の自動テストだけでは判定しない。

## 2. 既存の採用要件と範囲

- 2国家、小規模マップ、指揮官1〜3人、軍団、移動・攻撃・防衛、不完全情報、同時解決。
- 通常のゲーム開始時は各国1指揮官。国家差・特殊能力・物語的加入は今回作らない。
- 5分は入力の設計制約。オフライン版に強制カウントダウンを設けない。
- 固定スナップショットから解決し、同一状態・命令・seed・ルール版なら結果が同じになる。
- UI・AI・プレイヤー役エージェントには、許可されたObservationのみを渡す。
- M1で開発用CLIを用意する方針は採用済み。詳細な入出力契約は未決定。
- domainは型付きGDScriptのプレーンオブジェクト。UI、ファイル、DB、時計に依存しない。
- AI・操作画面・一括対戦・永続保存・リプレイはM2。オンラインは対象外。
- DB・実機方式の検証は開発計画のM1-B作業。ゲームルールの合意とは分けて記録する。
  DB選定を本書で先取りせず、保存実装前に検証結果をADRへ残す。

## 4. 勝利条件の比較（2国家用の旧案・現行仕様には適用しない）

| 候補 | 得られる体験 | 注意点 |
| --- | --- | --- |
| A・推奨: 首都占領、上限で引き分け | 劣勢側にも首都への迂回による勝ち筋が残る | 守り続けて引き分けを狙いやすい可能性 |
| B: 首都占領、上限で領土数判定 | 首都に届かなくても前進する理由がある | 領土優勢側の逃げ切りを強める可能性 |
| C: 重要拠点の保持で得点 | 拠点を取り返す攻防を継続させやすい | 得点・保持期間の説明と調整が増える |

Aの詳細案:

- 移動・全戦闘・退却・占領をすべて解決した後に勝敗を一度だけ判定する。
- 敵が自国首都を占領していれば敗北。双方が同じターンに条件を満たせば引き分け。
- 首都に入る命令を出した時点では勝利しない。途中の処理順でも勝敗を確定しない。
- ターン上限は仮に20。第20ターンを解決した後、首都による勝敗を優先し、
  決着しなければ引き分けとする。20という値は試遊で調整する仮説。
- 検証ツールの時間上限による中断は、ゲーム上の引き分けと分ける。
- 全軍喪失時の即敗北はD04・D06と合わせて決める。暗黙には追加しない。

## 5. 地図と命令の出発点（D02・D03・提案）

9領地の3×3グラフを比較用に置く。横・縦だけ隣接し、斜め・端同士は接続しない。
左右対称で、A首都は中段左、B首都は中段右。名称は仮の識別子。

```text
NW ─ NC ─ NE
│    │    │
AC ─ CC ─ BC
│    │    │
SW ─ SC ─ SE
```

- 初期領有案: 左列をA、右列をB、中央列を中立とする。中立軍は置かない。
- 通常開始案: 各国の指揮官1人と軍団を自国首都に置く。
- 2・3指揮官は最初から人数を配置した開発用シナリオで検証する。
  通常ゲームで1人から増える仕組みを採用したことにはしない。
- 指揮官1人に軍団1つを対応させ、1ターン1命令。兵種、軍団の分割・移管は扱わない案。
- 命令は「隣接領地へ移動」「現在地で防衛」の2種類。敵領・中立領への移動が侵攻になる。
- 未入力は防衛。確定前は変更可能、確定後は取り消せない案。
- 自分以外の指揮官、重複指定、非隣接移動、古いターンへの命令は確定前に拒否する。
  見えない敵の有無を理由に命令の受付結果を変えない。

すれ違いの比較:

| 案 | 同じ辺を逆向きに進む敵軍 | 含意 |
| --- | --- | --- |
| 通過・推奨 | 両方とも目的地へ進む | 防衛命令と裏回りの意味が明確。ただし首都交換になり得る |
| 辺で戦闘 | 道中で交戦し、勝者の移動継続等を別途定義 | 敵を進軍で止められるが、辺と領地の戦闘の連鎖が増える |

同じ領地へ着く敵軍同士は交戦する。味方は同じ領地に複数駐留でき、
戦闘時は協力するが指揮官・軍団自体は統合しない案。
到着前に出発した軍はその領地を守らず、敵のいない到着先は占領できる案。

## 6. 戦闘と継戦の検討事項（D04・D06・未決定）

推奨方向は「読みの成否を乱数で覆さず、防衛に意味があり、一度の敗北ですぐ終わらない」。
ただし、防衛が強すぎると1軍対1軍で突破できなくなるため、以下を同時に決める。

| 論点 | 次の検討で具体化するもの |
| --- | --- |
| 兵力 | 初期値、上限、0の軍団の扱い、整数での表現 |
| 防衛 | 補正量、到着した援軍への適用、敵のいない場所での効果 |
| 勝敗と同値 | 合計兵力との関係、同時侵攻の同値、防衛側がいる同値 |
| 損害 | 勝者・敗者の計算、複数軍団への配分、端数、全滅 |
| 退却 | 行先の選び方、所有判定の時点、敵到着先を避ける条件、退却不能 |
| 連鎖 | 退却先で再戦するか、退却軍同士の競合、1軍が同ターンに戦う回数 |
| 指揮官敗北 | 死亡・一時離脱・再配置のどれを採るか、通常開始1人での継続性 |
| 補充 | なし／自領で自動回復／首都のみ等。条件、量、処理時点 |

経済・補給線・購入操作は最初の候補から外す。自動補充まで省くかは未決定。
兵力が減るだけで勝ち筋が消える場合や、首都で回復し続けて突破不能になる場合を紙上で比較する。
現段階では戦闘式や退却先の自動選択を実装に委ねない。

## 7. 観測と結果（D05・提案）

- 地図の接続・首都位置・ルールは双方に公開する。
- 自分の指揮官・兵力・命令は正確に見える。敵命令は確定後も直接配信しない。
- 自軍の現在地と隣接地の敵軍を観測する案。所有するだけの無人領地が
  視界を供給するかは別途判断する。全領土から視界が出ると9領地では霧が消えやすい。
- 敵兵力はまず観測範囲で正確な数を出す案。概数にする場合は区分と丸めをSPEC化する。
- 領有情報を全体公開するか、軍勢と同じ視界に制限するかは未決定。
- 視界外の情報は「現在不明」と過去の観測を区別し、過去情報には観測ターンを付ける。
- 自軍が参加した戦闘結果は、解決後に視界外でも受け取れる必要がある。
  敵の退却先・残存兵力をどこまで出すかは個別に決める。
- 第三者視点の全戦闘ログをプレイヤーへ渡してから非表示にする方式は採らない。
- 終了理由は公開する案。終了後に全状態を公開する機能は別の判断とする。

観測はターン開始状態と解決結果のどの時点を参照するかを確定し、
イベントごとに受信者・公開フィールドを定義してから実装する。

## 8. 紙上で比較する3局面

以下は検討用の部分盤面。完成した解決例・テスト期待値ではない。

| 局面 | 盤面と秘密命令 | 現時点で説明できる結果／残る判断 |
| --- | --- | --- |
| 防衛を読む | A軍がCC、B軍がBC。AはBCへ移動、Bは防衛 | BCで戦闘。防衛の強さ・損害・退却を決めて期待値を記す |
| 裏をかく | A軍がCC、B軍がBC。AはBCへ、BはCCへ移動 | 通過案なら戦闘せず入れ替わる。BCの無人占領が首都勝利につながることを確認する |
| 中央で鉢合わせ | A軍がNC、B軍がSC。双方がCCへ移動、CCは空 | CCで同時侵攻戦。同値時の位置・損害・領有を決めて期待値を記す |

追加する境界例: 同時首都陥落、味方の援軍、防衛軍が出発した場所への侵攻、
退却先なし、退却先の同時占領、最終ターンの首都占領、視界外へ退却した敵のログ。
ルール採用後、兵力・前状態・双方命令・後状態・各国の観測を具体値で揃える。

## 9. 状態・進行・CLIの設計枠

技術契約もまだ案。ゲームルール採用後に次を実装可能な形式へ具体化する。

| 境界 | 定義する情報 |
| --- | --- |
| GameState | ルール版、seed、ターン、進行状態、地図、領有、国家、指揮官、軍団、終了結果 |
| Orders | 国家・対象ターン・指揮官・命令種別・移動先。入力全体を検証してから確定 |
| Resolution | 更新前状態を変更せず、更新後状態と内部イベントを返す |
| Observation | 観測者・対象ターン・可視状態・過去情報・本人の命令・配信可能な結果 |
| Application | 対戦開始、観測取得、命令検証と確定、双方確定の判定、1回だけの解決 |

既存TurnPhaseは語彙と遷移のみ。終局後に再び命令受付へ戻らない契約を追加する。
移動→戦闘→イベント→結果の内部で、退却・占領・補充・勝敗・観測の時点を明記する。
決定性は乱数をなくすだけでは満たせない。IDの安定した順序、端数処理、
同着処理、入力データの不変性まで検証する。戦闘に乱数を使わない案でもseedは保持する。

CLIは1プロセス内でセッションを保持し、JSON Linesで要求・応答する案。
プロセス終了時に対戦は失われる。M1でファイルセーブを代用実装しない。
開始・観測・命令確定・解決・結果取得を共通application経由で行う。
別途、以下を確定してCLI契約を作る。

- プロトコル版、要求ID、対戦ID、プレイヤー指定、コマンド名、JSON例。
- 手動の解決要求と双方確定時の自動解決のどちらを採るか。
- 不正JSON・不正命令・未確定・重複要求・終局後の要求に対するエラーと状態不変性。
- 標準出力をJSON専用にする起動方法、診断出力、終了コード、EOFの扱い。
- プレイヤー用出力と検証者用出力の分離。ローカルの検証者と対戦役の権限を混同しない。

## 10. M1の進行条件

M1-Aの完了条件:

- D01〜D06の判断結果を採用済みとして記録し、残す調整パラメーターと区別する。
- 移動・戦闘・退却・占領・終了・観測に、結果が一意に決まらない穴がない。
- 3局面と境界例を具体値で解決し、プレイヤー向け1枚ルールへ要約する。
- CLIの入出力・状態保持・確定条件・エラーを実装契約にする。

M1-Bで必要な検証:

- 不正な状態・命令を拒否し、拒否で状態や確定状況が部分的に変わらない。
- 両者の命令提出順、配列・辞書の並び順を変えても同じ結果になる。
- 未観測の敵状態だけを変えた場合に、許可情報が同じなら観測・受付結果も同じになる。
- 同着・同値・退却不能・首都交換・上限ターンを期待値と照合する。
- CLIで開始から終局まで手動指定の双方命令で操作でき、終了後は進行しない。
- DB・実機方式の検証状況を別記する。未選定・未検証ならM1-B全体の完了を宣言しない。
