兵0は「戦える兵なし」、隠蔽中は人数区分を出さず存在だけを示す。これはR09の表示パラメータとして扱う。

## 5. ユーザーへの選択質問にしない実装作業

次の5パッケージは、上のゲームルールの判断と区別して設計・検証する。
未実装の作業であり「確認事項を解消したので完成」とは扱わない。

1. **現行SPECの統合**: SPEC 002〜008の旧比較案・古い未決定表記を整理し、採用ルールと提案を分離。
   SPEC 009のターン順を優先し、受入例・1枚ルールを作る。
2. **決定的な解決とCLI**: 状態・命令・観測の契約、整数計算、ID順の端数配分、seedとルール版、
   CLIのJSON・エラー・不正命令検証を定義。API名などを一問ずつ確認しない。
3. **検証とバランス調整**: 複数国の衝突、同時首都陥落、復帰、情報漏えいの行動テスト。
   次に観測だけで動くAIとCLI対戦を整備し、R17〜R21を調整する。AIはまず均衡型1種類から。
4. **端末内保存の技術選定**: 埋め込みDB候補とGodot連携を公式情報・対象端末で検証してADR化。
   原子的保存・中断復帰・版管理を確認する。製品はまだ確定しない。
5. **操作とクリエイティブの検証**: 日本語・タップ・安全領域、5〜6指揮官と多数領土の購入操作が
   5分以内で扱えるか、ライセンス・素材目録とともに検証する。

古い保留表記の例: 指揮官上限、派閥への人数枠割当、人気・科学倍率、守備枠、購入の命令枠消費、

## 6. 了承済みの進め方と変更管理

R01〜R16とR17〜R21を出発点に、未記入の計算式・数値表・マップ配置を具体化する。
紙上検証で解決結果が一意になることを確認してから、対象ルールを実装する。
R22〜R24は後工程へ残す。既に了承された方針を一問ずつ再確認しない。

テストプレイでは次を優先して記録する。

- 戦闘の損害・撤退頻度、防衛の強さ、兵種とランクの費用に対する強さ。
- 資金・資材の不足や余剰、徴税・研究・人気向上・開発の選ばれ方。
- 指揮官の加入数・成長速度、中立部隊の密度、各派閥・初期位置の偏り。
- 試合の決着ターン、停滞・引き分け、5分以内に命令を入力できるか。

調整は変更前後のルール版・seed・命令記録・検証結果を残し、関係するSPECと数値表を同期する。
数値調整はこの暫定採用の範囲で進める。勝利条件・情報公開など遊び方を変える変更は、
理由と具体案を示してユーザーへ判断を仰ぐ。現在はゲーム未実装で、テストプレイはまだ実施していない。
